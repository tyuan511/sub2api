# Context

现有网关把 `APIKey.GroupID` 和 `APIKey.Group` 作为账号选择、权限、价格、计费和日志的共同上下文。`group_id = NULL` 不是简单的“无可用分组”，而是允许既有账号调度器从未限定的账号池选择。鉴权侧已经有 PostgreSQL → Redis L2 → Ristretto L1 的版本化快照，分组内已有 Redis 账号粘性、并发控制和多种账号选择策略。Channel Monitor V2 已保存分组请求、延迟和 token 聚合。

多分组能力不能只把 `group_id` 改成数组：请求过程中实际分组会变化，所有依赖旧字段的能力都必须在“选定本次物理分组”之后运行。同时故障状态需要跨实例共享，而路由配置、财务事实和审计事实需要跨重启和可核对。

# Goals / Non-Goals

## Goals

- 用户只在自己选择的同平台候选组内调度，并可控制配置顺序。
- 顺序和智能模式共用健康准入、故障转移和实际归属不变量。
- 智能模式由统一维度、不同权重产生可解释的动态顺序，不采用不可解释的随机分流。
- 成功率低于 50% 立即熔断，恢复后先探测、再给新会话、最后自然排空旧会话。
- 在缓存、数据库、Redis 和进程内存之间明确权威边界，控制热路径延迟与写放大。
- 单分组、旧客户端和历史未限定 Key 在灰度和回滚期间保持行为。

## Non-Goals

- 不创建自动纳入平台全部分组的公共 Auto 分组。
- 不跨平台或在第一阶段混用 standard/subscription。
- 不替代组内账号调度、账号粘性、并发限制和模型能力过滤。
- 不承诺供应商缓存能跨账号或分组迁移。
- 不在首次数据模型阶段一次性改写全部网关协议。

# Decisions

## 2026-09-06 补充：长期失败分组的近期恢复与成本回流

智能调度的目标是在用户可感知的成功率、延迟和会话稳定性护栏内降低实际费用。长期健康数据不能永久阻断已经恢复的低倍率候选，但近期恢复也不能一次性接管全部新流量。Builder 继续每分钟发布版本化快照，并额外读取最近 15 分钟聚合；该读取是辅助信号，失败时仍发布原有 1h/24h 评分，不能因为恢复观测查询故障改变既有调度可用性。

每个候选观测同时保存长期成功/失败计数与近期成功/失败计数。近期总样本至少 3 且成功率至少 90% 时标记 `recovery_eligible`，按近期成功数给出 500/2000/5000/10000 bps 的新会话流量上限；近期有失败时最高保持 2000 bps。长窗口低于用户 Key 的成功率门槛时，近期恢复信号可以暂时解除统计硬排除，但近期成功率仍必须达到该 Key 自己的门槛，不能用恢复逻辑绕过更严格的用户设置；恢复流量还必须通过确定性新会话采样。低于 3 个近期样本的候选继续使用原有低置信度/长窗口结果。

恢复流量按 `api_key_id + group_id + stable session hash` 做确定性采样，同一新会话在恢复阶段不会在候选之间来回抖动。已有组级 sticky 会话不重新进入智能排序；恢复只影响新会话。价格偏好下，已经通过恢复采样的低价候选置于稳定候选之前，使 0.07 倍率分组能够实际获得探测请求，而不是只在解释页面显示为恢复候选。若用户没有稳定 session hash，则恢复候选不抢占已有稳定候选。

恢复候选在任意硬失败后停止升档；所有候选都处于恢复状态时保留最佳努力顺序，避免恢复控制本身把请求变成 503。跨组故障转移仍遵守语义输出前的重放边界、组内优先、订阅/计费重新校验和实际组计费；恢复采样不改变这些不变量。新增恢复字段只进入版本化快照、路由解释和有界诊断事实，不进入普通单组请求。

## 2026-09-07 补充：成功率改为稳定性评分，不再硬拦截

用户滑条仍按 5% 一档（`smart_balance_bps` 0..10000，step 500）分配权重，但两端改为价格与稳定性，而不是价格与速度。令 `s = bps / 10000`：

- 价格 `1-s`：继续使用缓存修正后的费率倍数 `NormalizedRate`（费率倍数 × 缓存命中组成）。
- 稳定性 `s`：成功率 50%、首 Token 25%、整体耗时 25%。

成功率只进入稳定性分数，不再把候选标为 `success_rate_below_*` 或在共享快照/用户门槛上强制排除。整体成功率偏低时 Key 仍可调度，只是更稳的分组排在前面。`routing_min_success_rate` 保留存储与 API 兼容，但 UI 不再展示，排序与准入也不再读取用户门槛。Redis 熔断仍使用内部 50% 底线作为安全网；Redis 故障时按该底线 fail-open，不再因 80%/95% 用户门槛 fail-close。

## 2026-09-05 补充：用户连续权重与独立健康门槛

新增 `smart_balance_bps`（可空，0..10000）和 `routing_min_success_rate`（50..95，步长 5，新建默认 80）。新 UI 默认均衡，门槛重置为 80%，采用带刻度的胶囊轨道、白色圆形滑块和重置按钮，显示实际分项权重。旧 preset 在未编辑时保留，price/speed/balanced 回显为 1250/8750/5000 bps。迁移 249 只改变新建 Key 的数据库默认值；不修改已应用的 248、不回填旧 Key 或历史事实，已有 50% 和自定义门槛保持原值，编辑接口省略门槛时也不得套用新默认。

令速度比例 `s = bps / 10000`，评分为 `0.50*S + 0.10*C + 0.40*((1-s)*P + s*L)`；沿用价格缓存归一化和分项置信度收缩。比例在 active/canary/shadow 选择后强制应用，学习只优化分量估计，不能改动用户比例。

数据库保存配置及决策时的两个数值；鉴权快照升级为 v26。`route_version` 仍用于 CAS、outbox 和评分/决策失效；新增 `routing_state_version` 从迁移时的 route_version 初始化，候选集合不变时保留，以避免比例调整清空粘性和健康证据。修改候选集合/顺序时递增状态版本。使用记录仍按实际分组展示与计费。

新门槛同时用于本地共享窗口准入、Key 级 Redis Lua 熔断和管理端解释，默认最小样本量为 10。阈值升高使用现有滚动证据重新判断，不重置样本；降低门槛不直接关闭 OPEN。Redis 的 policy_version 单调前进，迟到的旧配置结果不能覆盖新门槛。冷却后仅单租约探测，RECOVERING 按比例放量；同一请求重复健康检查复用一次准入决定，避免抢到探测租约后又拒绝自己。已授予的恢复准入在非粘性智能请求中优先实际执行，正常排序不能把它变成无人执行的租约。

比例与门槛均为 Key 本地投影，复用原有共享快照，不按滑块值产生 Redis 评分副本或 metrics label。健康 CLOSED 快路径继续复用一次 Pipeline；门槛重判、OPEN/半开/恢复准入才增加有界原子 Lua。全部已知候选不达标不降门槛；严格门槛（包括新默认 80%）遇 Redis 故障时拒绝准入，显式 50% 和旧 Key 的 50% 兼容值保留原有故障降级契约。

单分组例外：表单仅在选择至少两个分组时显示上述控制。后端按配置中启用候选数量（在健康/请求资格过滤之前）确定 `RoutingEnabled`；单组请求计划使用 sequential，并在请求 context 中携带 Key ID/配置版本作用域内的禁用标记。公共 health/sticky 入口读到该标记后跳过组级 Redis 读写和健康拒绝，但保留失败统计与实际组计费，也不跳过账号级容错及安全/额度检查。多组因过滤只剩一个可用候选仍保持控制启用。无需数据库迁移或清空旧 sticky/breaker；管理路由解释返回 `routing_enabled=false` 且不读取无效的旧熔断状态。

本补充替代本文旧的固定 50% Key 门槛和“所有策略修改均切换粘性命名空间”描述；50% 仍是不可放宽的全局底线，恢复探测是受控例外。本地验证不等于环境上线；旧二进制不支持这些配置，回滚不得声称仍执行用户自定义门槛。

## 1. PostgreSQL 保存配置与事实，Redis 保存共享瞬时状态，内存保存只读快照

PostgreSQL 是 API Key、候选组、策略、版本、使用记录、账单、outbox 和异常路由事实的权威来源。Redis 保存鉴权 L2、路由粘性、熔断滚动计数、探测租约、评分快照指针和有界事件流。进程内 Ristretto/atomic snapshot 保存鉴权 L1、评分只读快照和可丢弃的短周期聚合。

请求热路径在 L1 命中时不访问 PostgreSQL。路由前最多一次 Redis 批量读取，路由后最多一次原子状态更新；对最多 8 个候选组做本地过滤和排序。

## 2. 使用独立有序关系表，同时镜像旧 `group_id`

`api_key_group_routes` 保存 `api_key_id`、`group_id`、连续 `priority` 和 `enabled`。`api_keys.group_id` 在兼容窗口内始终镜像 priority=0 的组。创建和修改路由必须在一个 PostgreSQL 事务里锁 Key、检查 `expected_route_version`、替换关系、同步镜像、递增版本并写 outbox。

旧客户端只传 `group_id` 时归一为单项 sequential 路由。新旧字段同时提交但首项不一致时返回稳定 400。

## 3. 显式区分历史未限定 Key 与新路由集合

历史 `group_id = NULL` 且没有 `api_key_group_routes` 的 Key 保持当前全局账号池语义，避免迁移造成线上行为变化。新客户端显式提交 `group_routes` 时必须有 1..8 项，因此不会产生空集合。已经采用新契约的 Key 如果所有候选因停用、删除、权限、能力或熔断被过滤，返回明确的无可用分组错误，绝不传 `nil groupID` 给旧账号调度器。

该兼容例外只服务迁移和回滚。后续若要取消“未限定 Key”，必须作为独立 breaking change 迁移。

## 4. 先选物理分组，再复用组内账号调度

新增 `RouteCoordinator` 位于协议 Handler 与现有账号选择器之间。它构造候选顺序、选择一个物理分组，然后以该组重新建立请求级 `APIKey`/Group 上下文，依次执行模型能力、用户订阅/权限、计费资格、利润控制和组内账号调度。

只有组内所有符合条件的账号在允许的重试范围内耗尽，且尚未产生语义输出时，Coordinator 才进入下一个组。客户端错误、内容策略拒绝、余额不足或已经产生语义输出均不触发跨组重放。

## 5. 智能调度是确定性动态排序

每个候选组先过硬门槛：权限、平台/计费类型、状态、模型能力、成功率和 breaker。有效统计窗口内访问成功率 `< 0.50` 立即 OPEN；恰好 0.50 不触发这条硬规则。

剩余候选使用成功率、价格、速度和容量统一评分。价格、速度、均衡只改变权重，不改变维度和硬门槛。排序使用稳定 tie-break：总分、用户 priority、group_id。评分快照包含版本和时间，单次请求固定使用同一版本。

## 6. 价格指标按真实 token 结构归一化

窗口逻辑输入等于普通输入、5m/1h/其他缓存写入和缓存读取之和。对该结构按当前有效分组/用户价格重定价得到预期成本；分母使用公共 1.0x 参考价并假设全部逻辑输入都以 cache read 计价，输出保持实际结构。两者比值为 `NormalizedEffectiveRate`。

评分只使用供应商报告的 `actual_usage`。`billable_usage`、ForceCacheBilling 和系统冷缓存补偿不能反向污染健康/价格模型。默认窗口 1h，样本不足依次回退 24h、平台基线和名义价格，并降低置信度。

## 7. 两级粘性和排空式恢复

组级路由粘性键包含 API Key、路由版本、会话、模型族和端点；选定组后继续使用现有组内账号粘性。切换后默认滑动保持 1h。原组恢复时进入 HALF_OPEN/RECOVERING：单租约探测成功后只接收新会话，已有备用组会话继续到 TTL 自然结束。只有备用组也不可用时才允许提前迁移。

主动故障转移导致的缓存冷启动单独记录 `actual_usage` 与 `billable_usage`。补偿有原因、上限和窗口，实际供应商成本与实际物理组不被改写。

## 8. 共享评分后台构建，用户价格最多在 8 个候选上本地投影

复用现有使用事实与 Channel Monitor 的分钟桶口径，但路由健康/价格桶由 `RoutingScoreBuilder` 独立维护，不依赖监控 V1/V2/off。Builder 通过 advisory lock 或租约保持单活，每 60 秒用独立后台连接池重算最近 10 个完整分钟，并按进程游标回填一个最多 30 分钟的历史块，最远 24 小时；游标在事务提交后推进，接管/重启可幂等重算，历史扫完后循环修复迟到事实。每张表每轮最多清理 5,000 个超过 7 天的桶；每块查询超时 15 秒、整轮 45 秒。生成共享输入和版本化快照后，先写完整版本再原子切换 current 指针。实例订阅/轮询指针并原子替换内存快照。持续优化关闭时只停普通决策采样与实验，基础失败/容量事实消费仍运行，避免成功率分母失真。

不为每个用户或 Key 建全量评分缓存。用户专属倍率只对本次最多 8 个候选本地重价和归一化。

## 9. 配置失效使用事务 outbox

路由变更和唯一 outbox 事件同事务提交。后台投递器删除对应 Redis L2、发布 L1 失效并更新依赖版本。节点即使错过 Pub/Sub，也会因 `route_version` 或依赖版本不匹配拒绝旧快照。outbox 投递必须幂等，失败可重试。

## 10. 异常事实异步化，财务事实保持可靠路径

正常首选一次成功只进入现有 usage 和内存聚合，不同步写完整 routing attempt。发生换组、全失败、breaker 转换、探测、部分输出或上游产生成本的链路进入有界 Redis Stream，再批量写 PostgreSQL。队列压力时可丢普通采样，但不得丢账单、usage、真实成本和最终实际组。

## 11. 分阶段发布

阶段 1 只建立向后兼容的数据/接口基础，不改变网关选择；阶段 2 接通用户配置 UI；阶段 3 上 sequential；阶段 4 上粘性/熔断；阶段 5 上指标和 smart；阶段 6 补齐所有协议、补偿、观测、压测和灰度。每阶段都有独立开关和回滚门禁。

## 12. 全量启用与单分组兼容（2026-09-06）

- 多分组基础路由不再按用户或管理员名单门禁，所有用户均可创建和使用多分组 Key。服务器不再提供独立的多分组总开关；请求是否进入组间路由只由该 Key 是否存在至少两个 `enabled=true` 的候选决定。
- 单分组、历史未分组和只有一个启用候选的 Key 继续使用原有分组、订阅、额度、账号调度、失败和计费路径。它们不读取或写入组级 sticky/breaker 状态，也不计算智能排名。
- 价格/速度/均衡、成功率门槛、熔断、近期恢复和跨组故障转移只作用于配置了多个启用候选的 Key。用户选择的候选集合仍是不可越界的硬边界。
- 用户 Key 管理页面直接展示多分组编辑能力；选择一个分组时隐藏调度、熔断和智能倾向控件，保存只产生单组 sequential 配置。历史单组 Key 的行为和实际组计费保持不变。
- 优化、个性化和模型增强继续由各自的策略开关控制。关闭优化只停止学习/实验控制环，不关闭确定性多分组路由、安全约束或恢复熔断。

# Risks / Trade-offs

- 兼容镜像造成短期双写复杂度；通过事务、唯一约束、route_version 和一致性巡检控制。
- 鉴权快照变大；候选数硬限 8，分组投影只选热路径字段，并通过快照大小与命中率指标监控。
- 按 Key/组/模型族建 breaker 可能产生较多 Redis key；使用 hash tag、TTL 和按实际访问懒创建控制基数。
- 组间重试会放大上游成本；只有无语义输出且失败分类允许时才切换，并记录所有异常链。
- 历史未限定 Key 是兼容特例；实现必须显式标识，不能把新路由集合耗尽错误地降级成该语义。
