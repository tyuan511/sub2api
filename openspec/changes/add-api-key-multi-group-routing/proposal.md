# Why

当前一个外部 API Key 只能显式绑定一个物理分组。分组内账号调度能够处理单账号故障，但整个分组不可用、容量不足或质量下降时，请求不能在用户认可的其他分组之间继续服务。直接把 Key 放进平台级公共自动池又会越过用户的价格选择边界。

本变更让用户为一个 Key 选择最多 8 个同平台、同计费类型的候选分组，并选择顺序调度或智能调度。智能调度仍以成功率为第一准入条件，再按价格、速度、容量等统一维度和不同权重动态排序。系统必须保护会话粘性、渐进回切和提示词缓存价值，并始终按实际成功的物理分组记录用量和计费。

# What Changes

- API Key 创建、编辑和读取接口新增 `group_routes`、`schedule_mode`、`smart_preference`、`route_version` 和乐观锁字段。
- PostgreSQL 新增有序候选分组关系、路由配置失效 outbox、异常路由尝试事实及使用记录路由字段；兼容期继续镜像 `api_keys.group_id`。
- 鉴权快照把候选分组整体物化到 Redis L2 和进程内 L1，请求热路径不查询 PostgreSQL。
- 新增 Key 级分组调度器：顺序模式按用户顺序；智能模式使用同一评分维度和不同策略权重动态排序。
- 新增 Redis 路由粘性、分组级熔断、半开探测租约、恢复排空和版本隔离；成功率低于 50% 立即熔断。
- 价格评分按窗口内真实输入、缓存写入、缓存读取和输出结构重定价，并以输入 100% 缓存命中的 1.0x 基准归一化。
- 分组内账号耗尽后才允许分组间故障转移；任何协议一旦产生语义输出就禁止跨分组重放。
- 实际使用记录、订阅扣减、利润控制和账单全部使用最终实际分组；系统触发的冷缓存损失使用独立、可审计的计费补偿字段。
- 用户端支持候选分组排序、顺序/智能模式以及价格/速度/均衡倾向，并展示预估倍率和评分解释。
- 新能力通过功能开关分阶段灰度，旧单分组 Key 和旧客户端保持当前行为且可回滚。

# Capabilities

## New Capabilities

- `api-key-multi-group-routing`: 定义多分组配置、动态排序、故障转移、粘性、熔断恢复、缓存补偿、实际归属、存储职责、性能预算和灰度要求。

## Modified Capabilities

无。仓库当前没有已发布的对应 OpenSpec capability；现有单分组行为作为兼容基线保留。

# Impact

- **数据库**：扩展 `api_keys`，新增 `api_key_group_routes`、配置失效 outbox 和路由事实字段/表；复用现有使用事实和分钟桶口径，路由聚合独立于 Channel Monitor 开关。
- **Redis**：扩展鉴权快照；新增带 `api_key_id`、`route_version` hash tag 的粘性、熔断、探测租约、指标快照和异常事件流。
- **后端**：API Key service/repository/DTO、鉴权缓存、各协议网关入口、账号调度编排、计费和 usage 记录均受影响。
- **前端**：API Key 创建/编辑改为可排序的多选候选组，并展示策略和预估倍率。
- **性能**：L1 命中时禁止回源 PostgreSQL；候选数默认最多 8，排序为有界内存计算；共享评分由后台单例构建。
- **兼容性**：旧 `group_id` 持续镜像首选组。历史 `group_id = NULL` 仍保留当前“不限定分组”的旧语义；只有显式采用新路由集合的 Key 才适用“空候选不得退化到全局账号池”。
