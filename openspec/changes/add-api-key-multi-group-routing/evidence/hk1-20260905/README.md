## 灰度中修复的问题

1. hk1 监控使用 V1，原先路由桶仅由监控 V2 维护，smart 因缺数据始终顺序降级。现由单例 Builder 独立进行有界窗口重算/历史回填/清理，V1 保持不变也能发布快照。
2. 原先基础失败事实被优化开关一起停掉，成功率分母缺失败样本。现在多分组开启即启动基础事实消费；优化关闭只停普通采样与实验。
3. `routing_decision != success` 被误判为高优先级，绕过采样。现普通决策和成功结果使用相同决策 ID 的稳定采样概率。0811 上 1,000 个全新 smart 会话全部命中评分，普通决策行数仍为升级前的 3,032，没有继续增长；基础失败/切换事件正常落库。

## 路由正确性

- `fixed-failover-sticky-partial.json`：首组 g0 返回 503 后，请求访问 g0→g1 并成功；g0 恢复后相同会话只访问 g1；g0 已输出语义内容再发送 SSE 错误时仅访问 g0，未向其他组重放。503 被容量分类而非健康失败计数，这是现有契约。
- `fixed-breaker-v3-before-recovery.json`：Key 70 的 5 成功/5 失败保持 CLOSED，第 6 个健康失败后 5/11 触发 OPEN，冷却期只访问 g7。
- `fixed-breaker-v3-recovery.json`：32 秒后探测进入 RECOVERING，30 个新会话渐进放量后 CLOSED，原备用会话依然只访问 g7。
- 熔断边界用同一 `gpt-4o` 模型族下六个不同模型名称注入失败，以免原有账号+模型瞬态保护在两次错误后先冷却账号、把后续请求变为容量溢出。前两轮相同模型试验只产生两个真实健康失败，不能算 `<50%` 边界验证，故不冒充通过。
- usage 中故障切换记录实际组 30、初始组 29、route_version=1、switch_count=1、cache_cold_due_to_failover=true；随后粘性请求实际/初始均为 30、switch_count=0。优化关闭仍能落下基础容量/健康/换组事实。
