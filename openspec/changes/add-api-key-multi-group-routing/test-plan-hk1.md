# hk1 多分组与智能调度测试方案

日期：2026-09-05。目标版本：`v20260905.1447`（5% 智能倾向滑块，含用户灰度名单）。

发布状态：hk1 已部署且健康，在线步长校验通过，当前灰度名单为 1 人且本次未改动。发布证据见 [5% 步长发布记录](evidence/hk1-20260905/step5-release.md)。以下功能测试用例仍需逐条执行，尤其空名单用例不得未经确认清空现有名单。

## 1. 目标与执行边界

验证「名单内开放新功能，名单外保持旧单组」，以及分组限制、5% 比例、成功率门槛、动态排序、故障转移、会话粘性、恢复、缓存与实际组计费。

本文件是待执行方案，不表示全部用例已经通过。部署只做只读冒烟，不自动加入用户、改动测试 Key、制造故障或调用付费上游。后续执行涉及以下条件时，应先明确对象和预算：

- 管理员指定可修改的测试用户/Key/分组；不使用真实用户正在运行的配置。
- 故障注入使用隔离的模拟上游和专用账号，不停用共享供应商，不停止 hk1 共享 PostgreSQL/Redis。
- 真实上游、图片/媒体任务和压测先明确模型、最大请求数、输出上限、费用上限；不能因“测试”默认无限调用。
- 只验证 hk1；us02 不在本方案执行范围。

## 2. 测试准备

### 2.1 最小资源

| 资源 | 准备方式与用途 |
|---|---|
| 管理员 M | 可编辑系统设置；默认不加入灰度名单，用于确认管理员无隐式豁免 |
| 用户 A | 指定灰度测试用户，测试加入、移出及恢复 |
| 用户 B | 始终不在名单中的对照用户；与 A 使用独立浏览器登录态 |
| G1、G2、G3 | 同平台、同计费类型、均对 A/B 有权限，倍率可区分；至少 G1 有两个隔离账号，便于测组内重试 |
| GX | 另一平台或不兼容计费类型；另准备无权限/停用分组供拒绝测试 |
| K-single | A 的单组 Key；另用 B 的普通单组 Key 作旧版对照 |
| K-order / K-smart | A 的两个独立 Key，分别配置 G1→G2→G3 顺序与智能模式；各故障场景使用独立 Key/窗口，避免旧熔断状态污染 |
| K-legacy | 经授权在专用测试 Key 上设置 1250、7350 或 8750 bps，验证历史非整档比例；不回填已有业务 Key |
| 模拟上游 | 能记录请求次数/时间、返回固定 usage、控制输出前 5xx、首字节延迟、流式中断与恢复；测试日志不保存凭据或真实正文 |

前端操作即可完成的最小集合是 M、A、B 和两个同平台分组；G3/GX/故障夹具可在后续阶段补齐。

### 2.2 冻结与记录

1. 确认所有 hk1 应用实例版本一致，记录镜像 ID、名单原值、各测试 Key 原配置及 route/state version；使用本次发布备份作为应用回退点。
2. 记录实际生效的总开关、breaker 窗口/最小样本/冷却、sticky TTL、评分版本与更新时间。代码默认值为 300 秒窗口、10 个最小样本、30 秒冷却、3600 秒粘性；若环境覆盖，以运行值为准，不能照抄默认值判定。
3. 用浏览器 Network 确认请求与回显。JWT 与管理员 API Key 仅由正常登录/既有授权凭据提供，不伪造身份、不放进截图、文档或命令历史。
4. 智能排序测试必须等待有效评分快照；使用新会话验证新排序，使用同一会话验证粘性。固定 prompt 可能命中同一会话，不能把重复请求当作独立新会话样本。
5. 每条用例记录结果：`未执行 / 通过 / 失败 / 阻塞`，附实际观察与证据，不以“没报错”代替预期断言。

## 3. 第一轮：快速验收（约 30–45 分钟，无需付费上游）

建议先按顺序完成以下 10 步，再进入故障演练：

1. M 打开「系统设置 → 功能开关 → 多分组与智能调度灰度名单」，记录当前名单。
2. B 打开新建/编辑 Key：仅显示旧单组选择器，无排序、熔断和智能倾向控件。
3. M 按 A 的用户 ID 搜索、选择并保存；A 刷新 Key 页面，能力接口应变为 true。
4. A 只选 G1：调度/门槛/倾向仍隐藏；选 G1+G2 后显示调度方式与门槛。
5. 切到智能模式，价格/速度默认 50/50；拖动与左右方向键按 5% 调整，端点为 100/0 与 0/100。
6. 设置价格 70% / 速度 30%，成功率门槛 85%，保存并重新编辑：比例与门槛回显一致，API 中 `smart_balance_bps=3000`、`routing_min_success_rate=85`。
7. 减到单组后保存：界面隐藏高级项，运行解释不启用组间控制；再打开多组 Key 验证未误改其他 Key。
8. B 仍保持旧单组；普通用户不能访问/修改管理员名单接口。
9. M 移出 A，A 刷新并仅修改 Key 名称：原多组配置不被隐藏表单清空；M 重新加入 A 后可恢复原候选与参数。
10. 恢复事先记录的测试配置/名单，记录实际增删的测试资源；不批量删除、不清空 Redis。

权重验收基准：先做健康/权限/容量硬检查，再对归一化且经过置信度处理的分项评分应用：

`Score = 0.50×成功率分项 + 0.10×容量分项 + 0.40×[(1-s)×价格分项 + s×速度分项]`，其中 `s = smart_balance_bps / 10000`。

| 价格 / 速度倾向 | 成功率权重 | 容量权重 | 价格权重 | 速度权重 |
|---|---:|---:|---:|---:|
| 100 / 0 | 50% | 10% | 40% | 0% |
| 70 / 30 | 50% | 10% | 28% | 12% |
| 50 / 50 | 50% | 10% | 20% | 20% |
| 30 / 70 | 50% | 10% | 12% | 28% |
| 0 / 100 | 50% | 10% | 0% | 40% |

必须用同一特征快照、同一候选集验证权重，允许浮点误差 `1e-6`；不能以“价格优先必选名义倍率最低”作为断言。成功率不达标的候选在任一倾向下都不得被高分复活。

### 6.1 成功率边界样本

先连续产生成功，再逐个注入失败，保证都属于同一个健康统计窗口/模型族/端点；确认实际组级分母，不用最终网关 200/500 数量替代尝试统计。

| Key 门槛 | 等于门槛时 | 再追加一次有效失败 | 预期 |
|---|---|---|---|
| 50% | 10 成功 / 20 总样本 = 50% | 10/21 ≈ 47.62% | 相等不触发该规则；下一次低于门槛后 OPEN |
| 80% | 16 成功 / 20 总样本 = 80% | 16/21 ≈ 76.19% | 同上 |
| 95% | 19 成功 / 20 总样本 = 95% | 19/21 ≈ 90.48% | 同上 |

若运行最小样本大于 20，先按同比例扩大相等阶段样本，再追加有效失败；每档使用独立 Key/状态，不能拿之前已 OPEN 的状态继续检验相等边界。账号级冷却可能先拦截请求，导致后续只记录容量不足而没有新的健康失败；须配置隔离夹具/足够账号并确认真实上游尝试已发生，不能为凑分母伪造记录。

## 7. P0/P1：价格、缓存、账单

| ID | 步骤 | 预期与证据 |
|---|---|---|
| B01 | 固定模型单价/倍率，模拟全命中、部分命中、无命中；覆盖长输入/短输出与短输入/长输出 | 归一化倍率使用窗口汇总 token，不是简单平均每条请求命中率；价格分项反映实际成本而非名义倍率 |
| B02 | 1000 输入、100 输出，输入/缓存/输出单价分别 1/0.1/2，同一单位，倍率 0.8；先全命中，再仅 100 输入命中 | 全缓存参考成本=300；全命中归一化倍率=0.8；部分命中实际成本=1110，归一化倍率=0.8×1110/300=2.96。该数字是隔离夹具验算，不是实际供应商报价 |

| B04 | 同会话故障切组产生冷缓存，主组恢复；另测试管理员移出名单 | 故障补偿仅针对可归因系统切换并受上限约束；不抹掉真实供应商成本。名单撤销可能回原组而冷缓存，不能默认等同故障补偿；按实际原因与配置核验 |
| B05 | 流输出后失败且 usage 为零/部分费用 | 不重放已输出内容；有效失败进入健康统计与诊断事实，不能以 `actual_cost > 0` 当作成功判定。此项是已知待补环境门禁，未验证前不得扩面 |

归一化参考：`有效倍率 × 窗口实际 token 成本 / 同一输入输出结构下的全缓存参考成本`。用户专属倍率、缓存写入费用和模型计价必须取该请求有效值；零 token/缺失单价的回退路径也需单测。预估倍率不是锁价承诺。

## 8. P1：性能与异常隔离

1. 先用模拟上游，同模型、相同请求数/输入输出长度/并发，比较：名单外单组、名单内单组、8 组顺序、8 组智能。每轮建议 1000 请求，先并发 1/8，再按资源余量升至 32；这不是已获授权的真实上游调用预算。
2. 分别测“新会话”与“相同会话”。仓库 `backend/cmd/api-key-routing-bench` 可测固定 prompt 流式 Chat，Key 仅用 `SUB2API_BENCH_API_KEY` 环境变量；固定 prompt 用例不能证明新会话排序开销，新会话应使用能明确设置有效 session 标识的测试驱动。
3. 记录最终成功率、成功 RPS、端到端 P50/P95/P99、语义 TTFT、输入/输出/总 token/s、实际组分布、换组率、Redis 命令/连接与 SQL 连接占用；同时保存 `/api/v1/admin/routing-optimization/runtime-metrics` 前后快照。
4. 单组组间控制应零 Redis 读写；名单资格缓存命中不查 DB，冷/过期按实例合并刷新而非按 Key 放大；Builder/事实消费者使用独立有界连接池。不要把普通鉴权/账号调度 Redis 访问误算作组间控制违规。
5. 新增路由总 P95 目标 ≤5ms；必须按同请求总开销或严格配对基线测量，禁止相加各阶段 P95，也不能用本地 map 微基准代替端到端指标。
6. Redis/DB/Builder/outbox 故障、单实例重启、多实例 TTL 与旧镜像回退在隔离拓扑演练；不停止共享测试环境依赖。验证空候选失败关闭、财务事实不丢、过期快照降级、恢复后不批量迁移健康会话。

## 9. 通过标准、停止条件与回退

- 可继续小名单试用：A/U 组全部 P0 通过；R01–R08 与 B03/B05 有受控环境证据；接口无越权、无越界路由、无重复重放/扣费。无法执行项标阻塞，不计通过。
- 可扩面：还须覆盖实际启用协议、真实上游成功、价格/缓存核账、完整观察窗口与性能预算。不同平台、端点、模型、计费类型分别抽样，不能只靠 OpenAI Chat 推断全部入口。
- 立即停止：任何名单绕过、跨未选组、语义输出后重放、重复计费、关键事实丢失；性能或成功率超出 runbook 护栏时停止扩面。观察期/样本不足时结论是“证据不足”，不是“稳定”。
- 回退优先移出专用测试用户或恢复原名单，不删除路由配置；必要时关闭多分组总开关并按备份替换应用镜像，保留数据库迁移与业务数据。旧于名单功能的镜像会忽略名单，必须配合总开关。
- 测试结束恢复本次明确改动的名单/Key/分组/账号；只回收此次创建且确认可清理的资源，不执行全局 Redis flush 或整库恢复。
